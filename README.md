# estate-next

Фронтенд сайта коммерческой недвижимости: Next.js 16 (App Router) + React 19 +
SCSS Modules.

Бэкенд — соседний репозиторий [`estate-api`](../estate-api) (Django). Без него
сайт поднимется, но покажет пустой каталог.

## Запуск

```bash
npm install
cp .env.example .env.local
npm run dev      # localhost:3000
```

Сначала поднимите бэкенд (`../estate-api`, `runserver` на :8000) и налейте
демо-данные — `python manage.py seed_demo`. Для показа заказчику:
`python manage.py seed_demo --photos` — подтянет настоящие фотографии.

## Страницы

| Маршрут | Что там |
|---------|---------|
| `/` | Каталог объектов |
| `/object/<slug>` | Страница объекта, собранная из блоков админки |
| `/privacy` | Политика конфиденциальности |
| `/consent` | Согласие на обработку персональных данных |

Slug задаётся в админке в поле «Адрес страницы» и меняется без разработчика.

Правовые страницы — **черновик**, написанный по типовой структуре 152-ФЗ под то,
что сайт реально делает. Перед публикацией их должен вычитать юрист. Тексты
лежат в самих `page.tsx` массивом `SECTIONS`, реквизиты подставляются из админки.
В «Правовых документах» админки ссылки на них заданы путём (`/privacy`), а не
полным адресом: при переезде на другой домен ничего чинить не придётся.

## Рендеринг

Статического экспорта здесь **нет** намеренно. Страница объекта целиком
собирается в админке, и правка блока должна доезжать сама, а не после
пересборки сайта. Отсюда сервер — Node или Vercel, GitHub Pages не подойдёт.

Ответы Django кэшируются на минуту (`REVALIDATE_SECONDS` в
`DEFAULT_REVALIDATE_SECONDS` в `src/services/Api/request/apiRequest.ts`): менеджер успевает увидеть правку, пока
переключается на вкладку сайта, а всплеск трафика не превращается во всплеск
запросов к API.

Главная пререндерится и обновляется по тому же таймеру, страница объекта
рендерится на запрос.

## Блоки

Бэкенд отдаёт плоский массив блоков с полем `type`, уже в нужном порядке.
`BlockRenderer` разбирает его через `switch` — так TypeScript сужает тип, и
внутри ветки блок уже конкретный.

```
src/components/blocks/
├── BlockRenderer.tsx      # type → компонент
├── ImageBlock/            # картинка во всю ширину
├── VideoBlock/            # свой файл в <video> или чужой плеер в <iframe>
├── TextBlock/             # текст, абзацы, пункты
├── ListBlock/             # плитки / строки / нумерованный
├── GalleryBlock/          # слайдер (Embla) или сетка
├── FaqBlock/              # раскрывающиеся вопросы
├── MapBlock/              # Leaflet + OSM, метка с окном и маршрутами
└── ContactsBlock/         # контакты + кнопка заявки
```

Добавить тип блока: модель и сериализатор на бэкенде → тип в
модель и enum в файле запроса
(`src/services/Api/endpoints/Estate/getEstateApi.ts`) → компонент → ветка в `BlockRenderer`. Неизвестный
тип пропускается — лучше страница без одного блока, чем упавшая страница.

## Данные: Api + Store

Слой API повторяет подход из `face`:

```
src/services/Api/
├── request/
│   ├── apiRequest.ts       # единая точка входа для всех запросов
│   ├── types.ts            # HttpMethod, ApiRequestConfig, ApiError
│   └── helpers/            # getApiBase, buildUrl, parseErrorPayload
└── endpoints/
    ├── Estate/getEstateListApi.ts   # + модели Estate, EstateKind, EstateStatus
    ├── Estate/getEstateApi.ts       # + модели блоков и BlockType
    ├── Site/getSiteSettingsApi.ts   # + SiteSettings, SocialLinkKind
    └── Lead/sendLeadApi.ts          # + SendLeadParams
```

Один файл — один запрос, модели лежат в нём же: что запрос принимает и что
возвращает, видно не выходя из файла. Отдельной папки `models` нет намеренно.

В `apiRequest` под капотом родной `fetch`, а не axios как в `face`: кэш Next
живёт именно на нём (`next.revalidate`), через axios страницы потеряли бы ISR.
Одна функция работает и на сервере, и в браузере.

Стор — RTK + rxjs + redux-observable, тоже по образцу `face`:

```
src/services/Store/
├── store.ts, rootReducer.ts, rootEpic.ts, hooks.ts
├── StoreProvider.tsx       # стор на дерево страницы
├── preload.ts              # сборка начального состояния на сервере
├── App/                    # общее для всех страниц: настройки сайта, футер
├── Estate/                 # каталог и страница объекта
└── Lead/                   # окно заявки и её отправка
```

На каждый запрос свой эпик (`Estate/epics/getEstateListEpic.ts` и т. д.),
вызывается через `dispatch`. Слайсы держат `isLoading`/`error`, компоненты
читают селекторами.

**Почему данные всё-таки грузит сервер.** Эпики живут в браузере, а страницу
объекта нужно отдать поисковику и мессенджеру уже заполненной. Поэтому первый
заход за данными делает сервер (`preload.ts`) и кладёт их в стор через
`StoreProvider` — как `initReduxStore` в `face`. Дальше страница работает как
обычное redux-приложение: эпики обслуживают всё, что происходит после загрузки.

Строковых юнионов в моделях нет — только enum (`BlockType`, `SocialLinkKind`,
`EstateKind`, `ImageBlockHeight` и остальные). Значения совпадают с
`TextChoices` на бэкенде.

## Заявки

Окно заявки одно на страницу, открывается из трёх мест: плавающая кнопка в
правом нижнем углу, кнопка в шапке и кнопка в блоке контактов. Открытие,
отправка и результат живут в слайсе `lead` — иначе на странице оказалось бы три
независимых формы. Значения полей остаются локальным стейтом формы: это
черновик, который никому больше не нужен.

Поля: имя, телефон, почта, комментарий. Телефон форматируется маской при вводе,
проверка формы — zod. Отправка идёт через `dispatch(leadActions.sendLead(...))`
→ `sendLeadEpic` → `POST /leads/`; бэкенд уже пересылает в телеграм, потому что
токен бота в браузер выносить нельзя.

## Карта

Leaflet поверх тайлов OpenStreetMap. **Ключ не нужен и платить не за что** —
поэтому не Яндекс и не Google: там ключ обязателен, а у бесплатных тарифов
есть суточные лимиты, при исчерпании которых карта на странице объекта просто
гаснет.

Библиотека грузится по требованию (`import()` внутри эффекта): весит заметно,
карта есть не на каждой странице, а в серверный рендер Leaflet тащить нельзя —
он обращается к `window` прямо при импорте. Не поднялась — остаётся адрес и
ссылка на внешние карты.

Тайлы идут с публичных серверов OSM. Это нормально для черновика и небольшого
трафика, но у OSM есть [условия использования](https://operations.osmfoundation.org/policies/tiles/):
под заметную посещаемость нужен свой тайл-сервер или платный провайдер тайлов
(MapTiler, Stadia). Меняется это одной строкой — адресом в `L.tileLayer`.

Если захотите родной для России вид — 2ГИС (MapGL) ставится на то же место,
но требует бесплатной регистрации и ключа.

## Аналитика

Яндекс.Метрика подключается компонентом `YandexMetrika` в корневом макете.
Номер счётчика — `NEXT_PUBLIC_YM_COUNTER_ID`; **пусто — не грузится ничего**:
ни скрипта, ни кук. Это рабочий режим для локали и стенда.

Цели перечислены в `src/lib/analytics/metrika.ts` (объект `Goals`) и должны
быть заведены в кабинете Метрики руками — тип «JavaScript-событие»,
идентификатор равен значению из кода. Незаведённая цель сайт не ломает,
события просто не попадут в отчёты.

Цели, следующие из жизненного цикла заявки (открыли форму, отправили, ошибка),
шлёт эпик `trackGoalsEpic`: побочный эффект не должен жить в редьюсере, его
повторно прогоняет devtools при перемотке. Остальные — прямыми вызовами
`reachGoal` в обработчиках кликов.

## Картинки

Домен бэкенда для `next/image` берётся из `NEXT_PUBLIC_API_URL` — держать его
в двух переменных незачем.

В разработке включён `dangerouslyAllowLocalIP`: Next 16 не оптимизирует
картинки с приватных адресов (защита от SSRF), а локальный Django живёт как
раз на `127.0.0.1`. В проде API на публичном домене, и запрет остаётся в силе.

## Что сделать перед продом

- `NEXT_PUBLIC_API_URL` — адрес боевого API, `NEXT_PUBLIC_SITE_URL` — домен сайта.
- Завести `NEXT_PUBLIC_YANDEX_MAPS_API_KEY`, иначе карты будут заглушками.
- Названия и тексты на главной (`src/app/page.tsx`) — сейчас общие: заголовок
  «Коммерческая недвижимость» и подпись под ним. Название компании и телефон
  в шапке уже тянутся из админки.
- Фавиконку (`src/app/` — файла пока нет, отдаётся дефолтная).
